# workflow-engine

Runs an item through its template: Start (worktree, setup), each step's attempts under the loop guards, done_when, if_failed, decisions, and Finish (the commit). The only slice that composes others.
The log is the state: every change is an event before the loop acts on it, and the loop resumes from the log after a decision or a restart. Commands (`startItem`, `resolveDecision`, `stopItem`) wait for restart recovery first.
Run failures (crash, quota, auth, timeout) ask and never count as attempts; work failures (checks, reviewer changes) count. A step entered again after a back starts a new round: `max_attempts` counts each round, and each step may send the work back 3 times before the item asks. Counters, grants, rounds and the budget come from the log (`counters.ts`).
Protection (`protect.ts`): files that steer Tokama (git config entries except the remote and tracking keys a push writes, with network URLs only, included config files, hooks, attributes, HEAD, `.tokama/`) are hashed once after setup passed at Start; any later change stops the item. Each staged tree is judged against the base commit; protected changes ask, and an approval covers that exact content. The checked, reviewed and committed tree is one tree.
Results: a step that sees an earlier step gets `{{ <step>.summary }}`, that step's final reply. A reviewer's reply must end with `VERDICT: approve` or `VERDICT: changes`; changes go back as a feedback block.
It also runs helpers (`helper-runner.ts`): one guarded, read-only agent call with no shell, in an empty folder of Tokama's own, whose inputs Tokama collects itself and whose answer is one JSON object. `prepare` makes every refusal (unknown helper, agent file, local-only, AI CLI not ready, cloud consent) before a run exists; `run` gathers, asks, and asks once more after a bad answer. The built-in Helper agent runs on the first ready CLI in `HELPER_TARGETS` (`helper-agent.ts`); an agent file of the person's own is used exactly as written.
Try checks (`check-trial.ts`) runs the commands a person accepted once, in a throwaway detached worktree at the base branch's commit, with no agent: `prepare` re-checks every command and the setup (one simple command, one line of plain text) and the worktree folder before anything exists; `run` makes the worktree, runs the setup, then every check even after one failed (a check is skipped only when the setup failed or the trial was cancelled), and removes the worktree in a `finally`. Output is the last 2,000 characters as plain text with our folders written as names.
Headlines: every agent step's instructions end with the `HEADLINE:` / `POINT:` / `READ: yes` block (`headline.ts`; a reviewer's verdict line stays last). The reply is read once the call ended (`parseHeadline` in `summary.ts`, tolerant, never throws) and what the agent said is stored on `attempt_ended` as `said`; a reply without the block gives its first lines, and nothing fails or retries. A reply is a must-read (`readMinutes`) when you approve text that changed nothing, when it is the last step of a template that ends with findings or a document, or when the agent flagged it and wrote 150 words or more. Helpers do not get the rule: their answer is one JSON object.
Plan lines: a step you approve that a step follows (the plan of Plan and build) is also asked for `CHOICE:`, `REACH:` and `RISK:` lines (`PLAN_RULE`, after the headline rule, kept after "Build anyway"). `summary.ts` reads them apart from the block labels, only in the run of block and plan lines at the end of the reply, so a prose line such as "- Risk: …" in the body stays text. The result is `said.plan` (7 choices and 3 risks at most, the rest counted), stored only when the step changed nothing; an empty plan says the agent left the lines out. Nothing is asked again for them. The log says per plan how much arrived (`full`, `partial`, `headline_only`, `missing`).
Must not spawn processes, run git or read config itself: the kernel and the other slices do, through the ports it is given.
